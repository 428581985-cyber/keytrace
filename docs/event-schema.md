# 事件格式 `events.jsonl`

> **状态**：草案，阶段 0 定稿。
> 阶段 2 可能会补充 `commit` 相关的字段，但**只加不改**（见文末「版本演进」）。

---

## 为什么先定这个文件

这个项目分四层，层与层之间只通过文件交接：

```
采集 → [events.jsonl] → 归因 → [stats.json] → 画像 → …
```

`events.jsonl` 是**唯一的上游契约**。它一旦定下来：

- 归因层可以拿假数据反复测试，不需要真的打字
- 别人写 Linux / macOS 采集器，只要吐出同样格式，后面三层一行都不用改
- 采集层内部换成 Raw Input 还是别的机制，下游完全无感

所以字段的取舍标准只有一条：**下游需要什么，就存什么；下游推不出来的，必须存。**

---

## 文件布局

| 项 | 约定 |
| --- | --- |
| 位置 | `%USERPROFILE%\.keytrace\events\YYYY-MM-DD.jsonl`（可用 `--out` 覆盖） |
| 编码 | UTF-8，无 BOM |
| 结构 | 一行一个 JSON 对象（JSONL），追加写，不重排 |
| 分片 | 按本地日期切文件；跨天不重建，直接开新文件 |
| 压缩 | 过完一天就压成 `.gz`；压缩包保留 30 天后删除。当天文件不动 |
| 轮转时机 | 启动时和跨天时各跑一次，长跑进程不用等重启 |

**为什么是 JSONL 而不是 SQLite / CSV**：纯文本能 `grep`、能用记事本打开、出问题时人眼能看，而且追加写不需要事务和锁。等到单日事件超过 50 万条、确实有性能问题了，再考虑上数据库——那时候的迁移成本远低于现在就引入数据库的复杂度。

## 一行长什么样

```jsonl
{"v":1,"ts":1731700000123,"mono":1234567,"ev":"kd","vk":78,"sc":49,"mods":0,"pid":1234,"exe":"WeChat.exe","sid":"20261116-1"}
```

## 字段表

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `v` | int | 是 | 格式版本，当前 `1` |
| `ts` | long | 是 | 墙钟时间，Unix 毫秒（UTC） |
| `mono` | long | 是 | 单调时钟，毫秒。**算时长只用它** |
| `ev` | string | 是 | 事件类型，见下表 |
| `vk` | int | `kd`/`ku` 必填 | 虚拟键码（Windows Virtual-Key） |
| `sc` | int | `kd`/`ku` 必填 | 扫描码，标识物理按键位置 |
| `mods` | int | 否 | 修饰键位图，默认 `0` |
| `pid` | int | 是 | 事件发生时的前台进程 ID |
| `exe` | string | 是 | 前台进程名，如 `chrome.exe` |
| `sid` | string | 是 | 会话 ID，见「会话切分」 |
| `text` | string | `commit` 必填 | 本次上屏的文本片段 |
| `src` | string | `commit` 必填 | 文本来源：`uia` / `ime` / `registry` |
| `keys` | int | `commit` 可选 | 促成这次上屏的击键数。**`0` 表示文本不是打出来的**（粘贴、拖拽、语音），归因层要排除 |

### `mods` 位图

| 位 | 含义 |
| --- | --- |
| bit 0 (1) | Shift |
| bit 1 (2) | Ctrl |
| bit 2 (4) | Alt |
| bit 3 (8) | Win |

例：`mods: 2` = 按着 Ctrl。

### `ev` 取值

| 值 | 含义 |
| --- | --- |
| `kd` | 按键按下 |
| `ku` | 按键松开 |
| `comp_start` | 输入法开始组字 |
| `comp_update` | 组字内容变化（含被退格删空） |
| `comp_end` | 组字结束 |
| `commit` | 文本实际上屏 |
| `comp` | 组字中间态（拼音字母、分隔符），**不是上屏** |

## 几个必须解释清楚的选择

### 为什么 `ts` 和 `mono` 都要

`ts` 是人类可读的时间点，但它**会跳**——系统对时（NTP）、用户手动改时间、夏令时，都可能让两个相邻事件的 `ts` 差出几秒甚至几分钟。

算"两个键之间隔了多久"必须用不会倒退的时钟，也就是 `mono`。Windows 上对应 `QueryPerformanceCounter`（高精度）或 `GetTickCount64`（毫秒级、不会因对时跳变）。

分工：**画图用 `ts`，算时长用 `mono`。** 两者都存，因为事后无法从其中一个还原另一个。

### 为什么 `vk` 和 `sc` 都要

- `vk`（虚拟键码）是**语义**：`65` = A 键。统计"我在 A 上错了多少次"要用它。
- `sc`（扫描码）是**物理位置**：同一个位置的键，不管键盘布局是 QWERTY 还是 Dvorak，扫描码都一样。

对打字训练来说两者都需要：想知道"某个字母练得怎么样"用 `vk`，想知道"某根手指对应的位置是否吃力"用 `sc`（换键盘、换布局时这个指标仍然可比）。

### 为什么存键码而不是字符

采集的时候**无法可靠知道**这一下按出来的是什么字符——中文输入法下面，`n i h a o` 五个键最终产出的是「你好」两个字，一对一关系根本不存在。

所以采集层只记"物理上按了什么"，字符那部分由 `commit` 事件单独记录，两者的关联是归因层的责任。这条边界必须守住：**采集层不做推断。**

## 事件类型与状态机

```
         ┌──────────── 英文 / 直接输入 ─────────────┐
kd ──────┤                                          ├──→ 上屏（由 UIA 差分得到）
         └── 触发组字 ──→ comp_start ──→ comp_update* ──→ comp_end ──→ commit
```

- `ku` 与 `kd` 成对出现，用于计算按住时长（dwell）
- `comp_update` 可能为零次（直接上屏）或多次（逐字打）或出现空串（被退格删掉）
- `commit` 的 `text` 是**本次新增**的文本，不是整段文档

**粘贴、拖拽、语音输入不产生 `kd`**，但会让 UIA 文本变化。归因层看到"文本变了但没有对应击键"时应直接丢弃——那段不是打字。

---

## 会话切分

一个 `sid` 代表一段连续的输入行为。规则：

1. 前台进程变化 → 新会话
2. 连续无事件超过 **5 秒** → 新会话
3. 日期跨越零点 → 新会话

`sid` 格式：`YYYYMMDD-HHmmss-序号`，例 `20261116-220105-2` 表示 2026-11-16 这一天、22:01:05 启动的那个进程里的第 2 次会话。

**为什么要把启动时刻编进去**：序号只存在进程内存里，重启就归零。如果 sid 只是 `20261116-2`，同一份日志里两次运行会撞号，按 sid 分组就会把两段无关的记录混成一段——会话时长、每分钟字数全错。带上启动时刻，重启后也不会重号，而且不必去读旧文件续号。

为什么需要会话：统计"每分钟字数"必须有明确的分母，否则中间去倒杯水回来，那一分钟的速度就是假的。

## 隐私

| 字段 | 敏感度 | 说明 |
| --- | --- | --- |
| `vk` `sc` `ts` `mono` | 低 | 键码本身不等于内容 |
| `exe` | 中 | 能反映你用什么软件 |
| `text` | **高** | 上屏的原文，可能含聊天内容 |

约束：

- **只在 `commit` 时记录文本**，绝不记录整段文档
- 排除列表命中的进程（密码管理器、银行客户端）**不产生任何事件**，连 `kd` 都不记
- 默认不联网、不上传、不同步
- 提供 `--no-text` 开关：只记键码，完全不落文本

## 示例：打「你好」

微软拼音输入 `nihao`，选中「你好」上屏：

```jsonl
{"v":1,"ts":1731700000100,"mono":1000,"ev":"kd","vk":78,"sc":49,"mods":0,"pid":1234,"exe":"WeChat.exe","sid":"20261116-1"}
{"v":1,"ts":1731700000180,"mono":1080,"ev":"ku","vk":78,"sc":49,"mods":0,"pid":1234,"exe":"WeChat.exe","sid":"20261116-1"}
{"v":1,"ts":1731700000300,"mono":1200,"ev":"kd","vk":73,"sc":23,"mods":0,"pid":1234,"exe":"WeChat.exe","sid":"20261116-1"}
{"v":1,"ts":1731700000380,"mono":1280,"ev":"ku","vk":73,"sc":23,"mods":0,"pid":1234,"exe":"WeChat.exe","sid":"20261116-1"}
{"v":1,"ts":1731700000500,"mono":1400,"ev":"comp_start","pid":1234,"exe":"WeChat.exe","sid":"20261116-1"}
{"v":1,"ts":1731700000900,"mono":1800,"ev":"comp_update","pid":1234,"exe":"WeChat.exe","sid":"20261116-1"}
{"v":1,"ts":1731700001100,"mono":2000,"ev":"kd","vk":72,"sc":35,"mods":0,"pid":1234,"exe":"WeChat.exe","sid":"20261116-1"}
{"v":1,"ts":1731700002200,"mono":3100,"ev":"comp_end","pid":1234,"exe":"WeChat.exe","sid":"20261116-1"}
{"v":1,"ts":1731700002210,"mono":3110,"ev":"commit","text":"你好","src":"uia","pid":1234,"exe":"WeChat.exe","sid":"20261116-1"}
```

归因层读这段能得出：**5 次击键，约 1.1 秒，产出 2 个汉字，没有退格**。这就是一次干净的输入。

## 录制边界

常驻录制没有"开始/结束"按钮，所以必须写清边界在哪里：

| 情形 | 行为 |
| --- | --- |
| 暂停期间（热键 / 托盘 / `keytrace pause`） | **零事件**。连键码都不记，文件里不会多任何一行 |
| 收到 `keytrace stop` | 落盘后体面退出；文件完整，不会留半个 JSON |
| 进程被强杀 / 崩溃 | 最多丢 1 秒（定时器每秒落盘一次） |
| **全局热键自身**（`Ctrl+Alt+P`） | **会被记成普通事件，2–4 条**。热键是系统级注册，按键在暂停生效前就已经到达采集层，无法事后撤回。归因层应按"含 Ctrl+Alt 修饰、无上屏文本、间隔极短"丢弃 |
| 停止瞬间按下的键 | 可能残留 0–2 个不成对的 `kd`（只按下、没等到松开）。下游按"有 `ku` 才成对"处理即可 |

## 组字中间态 `comp`

中文输入法会把组字过程（拼音字母加 `'` 分隔符）直接画进控件里，UIA 读到的文本和真正上屏的汉字混在一起。

举例：打「你好」时，文本区依次出现 `ni`、`ni'hao`、`你好`。前两个不是输入结果，是过程。

**判定规则**：文本增量全部是 ASCII，且当前输入法处于中文模式 → 记 `comp`；否则记 `commit`。

**为什么不用时间阈值**：试过"文本停 300ms 才算上屏"，实测无效——打字的人会停在组字中间想选哪个字，一停一两秒，拼音照样被判定为稳定。停多久取决于人在想什么，时间窗口设不了。

**代价**：中文模式下真的打英文单词（如打 `abc` 回车上屏）会被记成 `comp`。这种情况少，且下游可以从 `comp` 里取到同样的文本。

保留 `comp` 而不丢弃的原因：拼音层的错误（韵母键按错）只能从组字过程里看出来，这是阶段 3 归因的原料。

## 版本演进

- `v` 只增不减；解析器遇到不认识的 `v` 应拒读而不是猜
- **只加字段，不改语义**。给已有字段换含义等于制造一份新格式
- 新增可选字段时 `v` 不变；新增必填字段时 `v` 加一，并保留旧字段的解析路径
- 任何字段变更都要同步更新 `docs/` 和本文档，PR 模板里有这一项
