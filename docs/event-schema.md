# 事件格式 `events.jsonl`

> **状态**：`v1`，采集层已实现并实测。字段**只加不改**（见文末「版本演进」）。

---

## 为什么先定这个文件

这个项目分四层，层与层之间只通过文件交接：

```
采集 → [events.jsonl] → 归因 → [stats.json] → 画像 → …
```

`events.jsonl` 是**唯一的上游契约**。它一旦定下来：

- 归因层可以拿假数据反复测试，不需要真的打字
- 别人写 Linux / macOS 采集器，只要吐出同样格式，后面三层一行都不用改
- 采集层内部换成 Raw Input 还是别的机制，下游完全无感

所以字段的取舍标准只有一条：**下游需要什么，就存什么；下游推不出来的，必须存。**

---

## 文件布局

| 项 | 约定 |
| --- | --- |
| 位置 | `%USERPROFILE%\.keytrace\events\YYYY-MM-DD.jsonl`（可用 `--out` 覆盖） |
| 编码 | UTF-8，无 BOM |
| 结构 | 一行一个 JSON 对象（JSONL），追加写，不重排 |
| 分片 | 按本地日期切文件；跨天不重建，直接开新文件 |
| 压缩 | 过完一天就压成 `.gz`；压缩包保留 30 天后删除。当天文件不动 |
| 轮转时机 | 启动时和跨天时各跑一次，长跑进程不用等重启 |

**为什么是 JSONL 而不是 SQLite / CSV**：纯文本能 `grep`、能用记事本打开、出问题时人眼能看，而且追加写不需要事务和锁。等到单日事件超过 50 万条、确实有性能问题了，再考虑上数据库——那时候的迁移成本远低于现在就引入数据库的复杂度。

---

## 一行长什么样

按键：

```jsonl
{"v":1,"ts":1794844800486,"mono":1658177,"ev":"kd","vk":8,"sc":14,"mods":0,"pid":25908,"exe":"Code.exe","sid":"20261117-233222-1"}
```

上屏：

```jsonl
{"v":1,"ts":1794844804846,"mono":1662537,"ev":"commit","pid":25908,"exe":"Code.exe","sid":"20261117-233222-1","text":"你好","src":"uia","keys":12}
```

字段顺序固定（手写序列化，不走反射），所以日志人眼好读、diff 稳定。

## 字段表

| 字段 | 类型 | 出现于 | 说明 |
| --- | --- | --- | --- |
| `v` | int | 全部 | 格式版本，当前 `1` |
| `ts` | long | 全部 | 墙钟时间，Unix 毫秒（UTC） |
| `mono` | long | 全部 | 单调时钟，毫秒。**算时长只用它** |
| `ev` | string | 全部 | 事件类型，见下表 |
| `vk` | int | `kd` / `ku` | 虚拟键码（Windows Virtual-Key） |
| `sc` | int | `kd` / `ku` | 扫描码，标识物理按键位置 |
| `mods` | int | `kd` / `ku` | 修饰键位图，无修饰时为 `0` |
| `pid` | int | 全部 | 事件发生时的前台进程 ID；`meta` 恒为 `0` |
| `exe` | string | 全部 | 前台进程名，如 `chrome.exe`；`meta` 恒为 `keytrace` |
| `sid` | string | 全部 | 会话 ID，见「会话切分」 |
| `text` | string | `commit` / `comp` / `meta` | `commit`·`comp` 是本次新增的文本片段；`meta` 是键值对串 |
| `src` | string | `commit` / `meta` | 文本来源：`uia`（UI Automation 差分）/ `ime` / `registry` |
| `keys` | int | `commit` / `comp` | **本会话内**、自上次 `commit` 以来按下（`kd`）的次数。`0` 表示文本不是打出来的（粘贴、拖拽、语音） |

### `mods` 位图

| 位 | 含义 |
| --- | --- |
| bit 0 (1) | Shift |
| bit 1 (2) | Ctrl |
| bit 2 (4) | Alt |
| bit 3 (8) | Win |

例：`mods: 2` = 按着 Ctrl。

### `ev` 取值

| 值 | 含义 | 带 `vk`/`sc` | 带 `text` |
| --- | --- | --- | --- |
| `kd` | 按键按下 | 是 | 否 |
| `ku` | 按键松开 | 是 | 否 |
| `comp` | 组字中间态（拼音字母、`'` 分隔符），**不是上屏** | 否 | 是 |
| `commit` | 文本实际上屏 | 否 | 是 |
| `meta` | 会话元信息，每次启动和跨天各一条 | 否 | 是 |

> **只有这五种。** 阶段 0 的草案列过 `comp_start` / `comp_update` / `comp_end` 三个细分事件，阶段 2 实际实现时简化成单个 `comp`——UIA 差分只知道"文本变了"，区分不出组字的开始、更新、结束，硬造三个类型等于让采集层做梦。需要边界时用 `mono` 和相邻事件推。

### `keys` 的边界

两个限定条件，都是实测踩出来的：

- **只在同一会话内累计**。换应用或空闲超过 5 秒就清零。否则在浏览器里打的字会被算到记事本那次上屏头上——实测出现过 `keys: 42` 对应一段根本没打过的文本
- **只数 `kd`，不数 `ku`**，否则数字正好翻倍

`keys` 的主要用途不是精确计数，而是区分「打出来的」和「不是打出来的」。归因层实际只需要 `keys == 0` 这一个判断。

### `meta` 事件

每次进程启动写一条，跨天再补一条。`text` 是键值对串，`src` 说明从哪读的。

```jsonl
{"v":1,"ts":1794884942015,"mono":74,"ev":"meta","pid":0,"exe":"keytrace","sid":"20261117-110901-1","text":"ime=shuangpin/xiaohe","src":"registry"}
```

目前只有 `ime` 一个键，取值 `full-pinyin` / `shuangpin/xiaohe` / `shuangpin/ziranma` / `shuangpin/scheme-N` / `unknown`。

**为什么必须记**：全拼和双拼的键位负担完全是两套。微软双拼把 `ao` 放在 `c` 键、`sh` 在 `u` 键，所以 `c`、`u` 的使用频率远高于英文；换回全拼之后这套结论全部作废。没有这条，历史数据跨方案没法比。

`pid` 为 `0` 是刻意的：它不属于任何用户程序，写自己的 pid 只会让下游误以为那是某个应用的输入。

## 几个必须解释清楚的选择

### 为什么 `ts` 和 `mono` 都要

`ts` 是人类可读的时间点，但它**会跳**——系统对时（NTP）、用户手动改时间、夏令时，都可能让两个相邻事件的 `ts` 差出几秒甚至几分钟。

算"两个键之间隔了多久"必须用不会倒退的时钟，也就是 `mono`。Windows 上对应 `QueryPerformanceCounter`（高精度）或 `GetTickCount64`（毫秒级、不会因对时跳变）。

分工：**画图用 `ts`，算时长用 `mono`。** 两者都存，因为事后无法从其中一个还原另一个。

### 为什么 `vk` 和 `sc` 都要

- `vk`（虚拟键码）是**语义**：`65` = A 键。统计"我在 A 上错了多少次"要用它。
- `sc`（扫描码）是**物理位置**：同一个位置的键，不管键盘布局是 QWERTY 还是 Dvorak，扫描码都一样。

对打字训练来说两者都需要：想知道"某个字母练得怎么样"用 `vk`，想知道"某根手指对应的位置是否吃力"用 `sc`（换键盘、换布局时这个指标仍然可比）。

顺带一条实测结论：真人按键的扫描码从不为 `0`（一天 1948 条里 0 个为 0，共 48 种不同值）。**用 `keybd_event` 合成出来的事件扫描码全是 `0`**，所以下游可以拿 `sc == 0` 直接识别"这是自动化测试数据"。

### 为什么存键码而不是字符

采集的时候**无法可靠知道**这一下按出来的是什么字符——中文输入法下面，`n i h c` 四个键最终产出的是「你好」两个字，一对一关系根本不存在。

所以采集层只记"物理上按了什么"，字符那部分由 `commit` 事件单独记录，两者的关联是归因层的责任。这条边界必须守住：**采集层不做推断。**

## 事件类型与状态机

```
         ┌──────────── 英文 / 数字 / 符号 ─────────────┐
kd ──────┤                                             ├──→ commit
         └── 中文组字 ──→ comp（拼音中间态）────────────┘
```

- `ku` 与 `kd` 成对出现，用于计算按住时长（dwell）
- **不能假设一对一配对**：退格、方向键这类按住会连续触发的键，Windows 自动重复只发 `kd` 不发 `ku`。实测一天差 92 条，全部来自这三个键（退格 +41、右方向 +33、左方向 +18）。算按住时长要用「第一个 `kd` 到那个 `ku`」
- `comp` 可能为零次（直接上屏）或一次
- `commit` 的 `text` 是**本次新增**的文本，不是整段文档
- `meta` 每个进程启动写一条，跨天再补一条。它记录的是**配置**（输入法方案），不是行为

**粘贴、拖拽、语音输入不产生 `kd`**，但会让 UIA 文本变化。这类 `commit` 的 `keys` 为 `0`，归因层据此丢弃——那段不是打字。

---

## 会话切分

一个 `sid` 代表一段连续的输入行为。规则：

1. 前台进程变化 → 新会话
2. 连续无事件超过 **5 秒** → 新会话
3. 日期跨越零点 → 新会话

`sid` 格式：`YYYYMMDD-HHmmss-序号`，例 `20261116-220105-2` 表示 2026-11-16 这一天、22:01:05 启动的那个进程里的第 2 次会话。

**为什么要把启动时刻编进去**：序号只存在进程内存里，重启就归零。如果 sid 只是 `20261116-2`，同一份日志里两次运行会撞号，按 sid 分组就会把两段无关的记录混成一段——实测出现过 764 秒的内部空洞，会话时长、每分钟字数全错。带上启动时刻，重启后也不会重号，而且不必去读旧文件续号。

为什么需要会话：统计"每分钟字数"必须有明确的分母，否则中间去倒杯水回来，那一分钟的速度就是假的。

## 隐私

| 字段 | 敏感度 | 说明 |
| --- | --- | --- |
| `vk` `sc` `ts` `mono` | 低 | 键码本身不等于内容 |
| `exe` | 中 | 能反映你用什么软件 |
| `text` | **高** | 上屏的原文，可能含聊天内容 |

约束：

- **只在 `commit` / `comp` 时记录文本**，绝不记录整段文档
- 排除列表命中的进程（密码管理器、银行客户端）**不产生任何事件**，连 `kd` 都不记
- 默认不联网、不上传、不同步
- 提供 `--no-text` 开关：只记键码，完全不落文本

这不是洁癖。做探针的那晚，从记事本的焦点元素里原样读出了一段明文 GitHub token——本意只是测"能不能读到输入框内容"。任何全局读文本的工具都会顺带看到屏幕上的一切，包括你以为只放一分钟的密码。

## 录制边界

常驻录制没有"开始/结束"按钮，所以必须写清边界在哪里：

| 情形 | 行为 |
| --- | --- |
| 暂停期间（热键 / 托盘 / `keytrace pause`） | **零事件**。连键码都不记，文件里不会多任何一行 |
| 收到 `keytrace stop` | 落盘后体面退出；文件完整，不会留半个 JSON |
| 进程被强杀 / 崩溃 | 最多丢 1 秒（定时器每秒落盘一次） |
| **全局热键自身**（`Ctrl+Alt+P`） | **会被记成普通事件，2–4 条**。热键是系统级注册，按键在暂停生效前就已到达采集层，撤不回来。归因层应按"含 Ctrl+Alt 修饰、无上屏文本、间隔极短"丢弃 |
| 停止瞬间按下的键 | 可能残留 0–2 个不成对的 `kd`（只按下、没等到松开）。下游按"有 `ku` 才成对"处理即可 |
| 管理员权限的程序 | 采集不到，除非 keytrace 本身也以管理员运行（UIPI 隔离） |
| 输入法软键盘 / 语音 / 手写 | 没有物理击键，只会产出 `keys: 0` 的 `commit` |
| 编译前必须先 `keytrace stop` | 常驻进程锁着 exe，不停就编不动；硬编出来的还是旧版本 |

## 组字中间态 `comp`

中文输入法会把组字过程（拼音字母加 `'` 分隔符）直接画进控件里，UIA 读到的文本和真正上屏的汉字混在一起。

举例：打「你好」时，文本区依次出现 `nihc`、`ni'hc`、`你好`。前两个不是输入结果，是过程。

**判定规则（挂起替换法）**：文本增量全是 ASCII 时先挂起来不发，观察它后面会变成什么。

- 随后出现非 ASCII（汉字或中文标点）→ 那段 ASCII 是拼音，记成 `comp`，同时把汉字记成 `commit`
- 挂满 **1800ms** 仍没有汉字 → 它就是要上屏的内容（英文、数字、符号），记成 `commit`

写文件之前还有一层：文本要**静置 300ms** 不再变化才处理，否则每擦一个字母都会被采样一次。

**为什么不用输入法状态判断**：`ImmGetConversionStatus` 对微软拼音返回英文态。Win11 的微软拼音和绝大多数应用都走 TSF，没有 IMM32 上下文，这个 API 在 TSF 时代已经废了。试过，实测无效。

**为什么不用短时间阈值**：试过"文本停 300ms 就算上屏"——打字的人会停在组字中间想选哪个字，一停一两秒，拼音照样被判定为稳定。停多久取决于人在想什么，时间窗口设不了。

**代价**：中文模式下真的打英文单词（如打 `abc` 回车上屏），要等 1.8 秒才记成 `commit`，时间戳比实际晚，内容不丢。

保留 `comp` 而不丢弃的原因：拼音层的错误（韵母键按错）只能从组字过程里看出来，这是阶段 3 归因的原料。**注意 `comp` 只有一条**——记的是最终那版拼音串，不是逐字符的中间态序列，因为 300ms 静置已经把中间态滤掉了。要看逐键过程用 `kd` 序列。

## 版本演进

- `v` 只增不减；解析器遇到不认识的 `v` 应拒读而不是猜
- **只加字段，不改语义**。给已有字段换含义等于制造一份新格式
- 新增可选字段时 `v` 不变；新增必填字段时 `v` 加一，并保留旧字段的解析路径
- 任何字段变更都要同步更新 `docs/` 和本文档，PR 模板里有这一项
